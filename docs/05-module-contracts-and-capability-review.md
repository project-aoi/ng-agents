# 模块精确定义与用户需求检验

本文补全 [8 模块架构](./02-atomic-kernel-architecture.md) 的运行契约，检验“用户正常想做的事能否组合实现”。这是设计提案，还没有对应的运行时代码。

判断标准：只有在遵守模块契约时无法实现需求，才算该版本的能力边界。字段未列出、实现有 Bug、需要写业务逻辑、需要安装连接器，都不单独算“架构拼不出来”。不能把任意后台服务塞进 Workspace 后声称已有能力，也不能为了制造反例，任意禁止原文允许的代码执行或状态持久化。

## 1. 补定义与改架构的分界

以下标记贯穿本文：

- **澄清**：明确原有概念，不引入新的运行路径。例如消息 ID 与业务任务 ID 不相同。
- **契约扩展**：原最小接口不能完整表达，需要增加操作、状态或通路。例如运行中的取消信号。扩展可以留在 8 个模块内，但不能称为“只改个名字”。
- **外部条件**：能力由外部服务、设备、网络或部署决定。例如源系统有没有撤回接口。

本文最终定义称为 **C1 契约**。第 5 节分别说明：哪些需求迫使我们扩展了原接口，以及扩展之后还剩什么边界。C1 能支持一个功能，不等于原来的百行接口已完整支持它。

### 1.1 相对原接口的扩展清单

| 编号 | 原接口或表述 | C1 明确定义的变化 | 性质与对应需求 |
| --- | --- | --- | --- |
| E1 | `sessionKey` 关联会话与执行，`exec` 返回一次工具结果 | 分离 Session / Task / Run / Job；增加 Job 启动、观察、取消和完成事件 | 契约扩展：同一聊天中边执行长任务边处理新问题 |
| E2 | 普通消息经 `claimNextRun` 领取，原文另有 `steer` 目标 | 授权控制信号可在 Run 活跃时生效；定义取消生效点及任务版本校验 | 契约扩展：执行中停止或改变要求 |
| E3 | Context 主要提供快照、日志、检索与 `mutateKnowledge` | 分离业务状态、证据和知识；增加带版本的读取及状态/意图原子提交 | 契约扩展：自动维护项目、并发编辑草稿、持久化等待与依赖 |
| E4 | Agent Loop 被描述为推理循环 | 注册确定性处理器和模型处理器；明确业务编排规则的执行位置 | 契约扩展：无模型审批、保存表单、子任务汇合 |
| E5 | `trust` 标记来源可信度，Gate 检查 ProposedAction | 身份与证据来源分离；授权绑定动作/产物版本；增加能力撤销和预算预留/结算 | 协议扩展：跨设备确认指定版本、受控发布知识与停止后阻止新动作 |
| E6 | Outbox 发送消息或 `silentDrop` | 区分命令、内部结果、通知和暂态预览；增加投递查询与待发取消 | 过滤作用域的澄清及接口扩展：免打扰不中断后台协作、流式展示 |

以上均为本次提出的设计定义，不代表已有实现。第 3 节给出职责、操作与约束，第 4 节给出可执行的组合协议。

## 2. 必须分开的对象

| 对象 | 精确定义 | 关系与状态归属 |
| --- | --- | --- |
| Principal | 经过认证的用户、服务或 Agent 身份 | Channel 验证外部身份；Gate 决定权限。消息正文不能自报身份取得权限。 |
| Session | 一段对话及其展示顺序 | Context 保存对话；一个 Session 可以关联多个 Task。它不是工作区、权限边界或所有业务对象的互斥锁。 |
| Task | 有目标、负责人、生命周期和验收条件的业务事项 | Context 保存；可跨 Session 延续，可包含多个子 Task。 |
| Run | 某个处理器的一次有界执行尝试 | Inbox 管领取、租约与运行状态；恢复材料存 Context。一个 Task 可以经历多个 Run。 |
| Job | Workspace 中实际运行的命令、测试或工具操作 | Workspace 管进程、输出、结束与取消。Job 可以长于启动它的 Run。 |
| Action | 一次具有确定目标、参数和前置条件的动作提案 | Context 保存提案及业务结果；Gate 保存对应授权。批准不等于已经执行。 |
| Artifact | 草稿、报告、代码差异等带版本的产物 | Context 保存已发布版本和元数据；Workspace 保存工作副本。 |
| Envelope | 对事件、命令或结果的一次传输 | Inbox / Outbox 保存收投记录；传输 ID 不代替 Task、Action 或 Artifact 的 ID。 |

### 2.1 消息协议

以下是逻辑字段，不限定数据库列名：

```typescript
type MessageKind = "event" | "command" | "result" | "control";

interface Envelope<T> {
  id: string;                  // 同一传输重试保持不变
  tenantId: string;
  from: string;
  to: string;
  principalId: string;         // 由可信接入层绑定
  kind: MessageKind;
  type: string;                // 已注册、带版本的 payload schema
  sessionId?: string;
  taskId?: string;
  causationId?: string;
  correlationId?: string;
  expectedRevision?: number;
  createdAt: number;
  expiresAt?: number;
  payload: T;
}
```

`type` 对应处理器注册表；未知类型拒绝或进入隔离队列，不能靠模型猜测它的控制含义。`control` 只允许已注册的控制命令，例如取消、暂停、转向；收到该类型本身不赋予权限。审批回执必须绑定具体 Action 版本。

原 `trust` 字段拆成两个不同问题：**谁有权发起动作**由身份和 Gate 判断；**内容来自哪里、能否作为依据**由 Context 的来源记录判断。外部邮件可以是“客户已回复”的证据，但不能因为被后台总结了一遍就变成系统指令。

### 2.2 状态与生命周期

- Task 的生命周期为 `open | completed | cancelled`；推进状态为 `ready | running | waiting | paused | blocked`，只用于未结束任务。
- `Agent / Human / External` 是动作的推进责任方，不是完整生命周期。一个项目可以同时拥有这三类动作。
- Waiting 必须保存等待条件：事件类型、关联对象、匹配规则和可选截止时间；不只是自然语言“等一下”。
- Run 以 `completed | yielded | failed | cancelled` 结束。`yielded` 必须引用已持久化的等待条件或仍在运行的 Job。
- Action 至少区分 `proposed | awaiting_approval | ready | executing | succeeded | failed | unknown | cancelled`。`unknown` 表示外部结果尚无法确认，不等于失败或成功。
- 草稿编辑产生 Artifact 新版本；审批绑定被展示的版本。新的编辑不会隐式获得旧版本的批准。

每个注册处理器还要声明执行预算、executionKey 规则、输入 schema 和允许请求的动作类别。达到本次 Run 的时间或步骤上限时，保存检查点后让出执行；若已启动 Job，则保存其句柄。不能通过把一个无限循环称为“一次 Run”规避调度契约。

## 3. 八个模块的封闭职责

“封闭”指每个模块都有允许的操作与禁止承担的责任。业务可以增加自己的任务 schema 和处理规则，但不能通过新增 schema 获得新的系统权限或副作用通道。

### ① Channel：外部协议适配

**输入输出**：外部请求、Webhook、UI 命令 → 经认证的 Envelope；投递请求 → 外部协议响应或投递结果。

**操作**：`receive`、`deliver`、`capabilities`。能力描述必须说明能否查询发送结果、撤回、条件更新、接收事件和传输流式内容。

**拥有**：连接、外部游标、身份映射、协议重连状态。**不拥有**：项目真值、审批规则、任务依赖和业务完成判定。

UI 可以本地编辑尚未提交的草稿；提交业务修改时必须发送命令。外部消息先持久接收再确认收件。音视频或大文件可以用有权限的流/文件引用传输，不能声称任意外部数据源天然可接入。

### ② Clock：产生时间事件

**操作**：`schedule(rule, messageTemplate)`、`cancel(timerId)`、`reschedule(timerId, revision, rule)`。

**拥有**：定时规则、时区、触发次数、下一次到期时间和取消版本。**不拥有**：是否应该催客户、是否已收到回复等业务判断。

一个具体触发实例有稳定 ID。取消防止未来触发，不能把已投递的事件从历史中抹掉；处理器需验证对应等待项是否仍有效。Idle 的作用域必须指定为某个 Session、Task 或用户，不能假定整个系统同时空闲。

### ③ Inbox：持久接收、调度和运行控制

**操作**：`enqueue`、`claim(executionKey)`、`renewLease`、`finish`、`signal(runOrTask, control)`。

**拥有**：队列、去重记录、领取租约、运行注册表和控制信号的送达状态。**不拥有**：项目业务状态或任务验收规则。

串行化对象是 `executionKey`：对话更新可按 Session 串行，独立任务按 Task 执行。长 Job 运行期间不持续占用对话处理锁。业务资源冲突由 Context 条件提交解决，不能用聊天会话锁代替。

**契约扩展：控制通路。** 经 Gate 授权的取消/暂停可以在普通 Run 活跃时被接收和应用，不等待该 Run 领取下一批工作。持久化取消状态后，撤销对应动作能力并通知 Workspace；任务树取消需按持久化子任务关系传播。控制处理器不调用模型理解已注册的取消命令。

取消的生效点是权威取消记录提交。任务控制提交与执行入口的动作准入须按同一任务版本条件串行提交，不能先读一次状态再无条件执行；取消之后不得接受该任务的新动作。此前已准入的在途动作尝试中止，并报告实际结果或未知结果；后续能力撤销和进程停止可以异步传播。不能把“用户按下按钮”与“远端动作已撤回”混为一谈。

### ④ Context：持久业务状态、证据与推理快照

**操作**：`read`、`query`、`commit(expectedRevisions, patches, intents)`、`appendEvidence`、`hydrate`、`proposeKnowledge`、`publishKnowledge`。

**拥有三类分离的数据**：

1. **业务状态**：Task、Project、依赖、等待条件、Action 提案、Artifact 版本和 Run 检查点。使用注册 schema、访问控制和版本条件提交。
2. **证据**：原始消息、工具结果、来源、时间、可见范围。外部证据允许保存，不因此取得指令权限。
3. **知识与规范**：偏好、可复用事实、`SKILL.md`；记录来源与适用范围，发布为可执行规范需要相应授权。

`hydrate` 只生成有版本、有权限范围的推理视图，快照和摘要不是业务真值。长期记忆压缩不能删除项目的权威状态。

**契约扩展：结构化提交。** `commit` 对一次授权范围内的业务读集验证版本，并原子提交状态变更和待投递意图；失败时全部不提交。处理器重新读取后决定如何处理冲突。跨租户以及外部系统不属于这个事务。

意图由持久化投递器经 Outbox 发送；Outbox 以意图 ID 去重接收，发送到 Inbox 后重复事件仍按 ID 去重。投递器可以重放未确认意图。这是 Context 与 Outbox 的提交协议，不是假设两个独立数据库自动具有事务。

Context 不决定“下一步做什么”，只验证存储契约、保存处理器的决策。`mutateKnowledge` 不能继续同时充当任意项目状态修改入口。

### ⑤ Agent Loop：有界事件处理与推理

**操作**：`handle(batch, snapshot, ports, signal)`，产生状态变更提案、动作意图或等待检查点。

**拥有**：当前执行的临时计算状态。**不拥有**：只能留在进程内的唯一任务真值、隐藏定时器或不可恢复的待办列表。

**契约扩展：处理器有两种模式。** 已注册的确定性处理器执行审批回执、任务汇合、UI 编辑提交等规则；模型处理器做理解、规划和内容生成。确定性规则使用版本化业务代码，不要求每次调用 LLM，也不允许 LLM 临时改写规则取得权限。

处理器只能通过授权 ports 请求 Context、Clock、Workspace 和 Outbox 操作。模型可能做错业务判断，架构的可表达性不代表模型推理必然正确。

多 Agent 编排是本模块执行的应用协议：依赖、预期子任务集合、汇合条件、超时和取消策略保存在 Context。不能把“Outbox 能寻址”直接等同于“编排已经完成”。无状态指 Run 可替换；不代表整个任务没有持久状态。

### ⑥ Workspace：受控执行与产物工作副本

**操作**：`acquire`、`startJob`、`observeJob`、`cancelJob`、`publishArtifact`，以及可选的 `hibernate / restore`。

**拥有**：执行环境、Job 生命周期、工作文件、进程和执行输出。**不拥有**：另建一套项目数据库、常驻调度器、权限系统或绕过 Gate 的业务出口。

**契约扩展：Job 句柄。** 启动后返回稳定句柄；完成事件送回 Inbox，状态可查询。推理 Run 不必保持打开等十分钟测试。交互式进程可用显式 Job 输入/输出流继续交互；生存期、资源配额和持有能力必须受管理。

任意代码执行只意味着在授权环境内计算，不意味着任意网络、任意身份或无限进程权限。对外副作用必须经过受管代理或受约束的执行边界；不支持可中断执行的连接器必须显式声明。

### ⑦ Gate：动作授权与能力约束

**操作**：`authorize`、`approve(actionVersion)`、`reserveBudget`、`settleBudget`、`revoke`、`checkCapability`。

**拥有**：权限策略、审批记录、能力令牌和预算预留/结算。**不拥有**：任务推进计划或内容事实真伪的最终判断。

授权对象包含 Principal、租户、动作内容版本、目标资源、Task 版本、有效期和权限范围。执行入口验证授权仍有效；过期或已撤销的提案不能直接发送。

权限检查覆盖模型、确定性处理器和 Workspace 代码。预算需要在启动有成本的工作前预留；无法估计最大成本且服务端不支持限额的调用，不承诺严格金额上限。这是外部条件，不是新的业务功能反例。

### ⑧ Outbox：结果与命令的投递

**操作**：`submit(intent)`、`status(intentId)`、`cancelPending(intentId)`、`preview(stream, chunk)`。

**拥有**：待投递记录、重试、投递结果、通知缓冲和预览流。**不拥有**：任务是否成功、依赖是否满足、用户是否已经授权的独立判断。

投递项必须区分：业务命令、内部结果、给人的通知、暂态预览。免打扰与 `NO_REPLY` 只作用于通知，不能吞掉子任务结果、控制命令或业务状态变更。预览可以丢弃重建，最终产物必须另行提交；预览不能携带需执行的业务命令。

实际投递前验证 Gate 能力和任务版本。外部渠道支持幂等时沿用动作 ID；否则显式保留未知结果，不虚构通用的“对外恰好一次”保证。

## 4. 组合规则：业务逻辑具体放在哪里

应用由三件东西构成：**Context 中注册的业务 schema、Loop 中注册的处理器、Gate 中注册的策略**。它们可以共用一个进程，也可以独立部署；“8 模块”不规定服务数量。

这是允许的扩展点。新增协议适配器归 Channel，新增时间规则归 Clock，新增执行工具归 Workspace。新增能力如果没有对应的现有操作和权限语义，必须修改契约，不能仅写进一个任意 JSON 字段。

例如“让 A、B 分别调研，两份报告都完成后汇总”的具体协议：

1. 处理器提交父任务、子任务 A/B、确定的预期集合 `{A, B}` 和两条派发意图。
2. 子任务分别使用独立 executionKey / Workspace，完成时发布产物版本和结果事件。
3. 父处理器按子任务 ID 和任务版本记录结果，条件提交检查是否满足 `all({A, B})`。
4. 从“等待结果”到“可汇总”的转换只能成功一次，同时提交汇总意图；重复结果不再次触发。
5. 缺失结果按已注册超时规则处理；父任务取消后，旧版本的子结果可以归档，但不能复活汇总任务。

这里没有新增第 9 类基础模块，但确实实现了编排协议。仅连上两条消息线不等于完成上述工作。

## 5. 从正常用户需求反推边界

### 5.1 三个用于检验契约的场景

以下是**条件反例**：只在保留列明的限制时不可满足。它们不是“任何 8 模块实现都做不到”的证明。

#### A. “测试继续跑，我先问另一个问题；我说停时立即开始停止它。”

若一次 `run` 持有 Session 锁并等待同步 `exec` 结束，且所有新消息都等下一次 `claim`，那么用户的新问题和停止命令都只能等测试结束。提高队列优先级不能抢占已经领取的任务；再加一个 Agent 也不能自动停止原进程。

必须允许长 Job 脱离 Run，并让取消信号在普通工作锁之外生效。C1 的 Inbox 控制通路、Workspace Job 句柄和 Gate 撤销共同支持它。原文已提出 `steer`，所以这是兑现原有目标所需的契约扩展，不能把原文解释成明确禁止中断。

**C1 结果**：支持边聊边执行、取消未提交动作、停止可中断 Job。远端已经发送的邮件是否能撤回取决于外部能力。

#### B. “客户一回复就自动更新项目；我同时改草稿，别把我的修改覆盖掉。”

若 Context 只允许拼提示词、追加对话和写长期知识，且外部内容使整个回合不能写入，那么客户回复既不能成为合法业务更新，也没有带版本的草稿提交路径。把所有外部内容升级为可信才能写入，会改变原有权限约束。

必须把外部证据、业务状态和可执行知识分开；草稿及任务按对象版本提交。C1 明确增加这套契约，允许“记录并应用客户回复”，同时不赋予邮件正文修改权限策略的能力。

**C1 结果**：支持。冲突时保留人的已提交版本，并让 Agent 重读/重做；逐字自动合并仍需应用定义编辑操作或合并规则。这里不声称带版本写入本身就等于完整协同编辑产品。

#### C. “我开了免打扰，但后台调研照常汇总，批准过的工作照常推进。”

若 Outbox 把所有输出当作可静默丢弃的通知，子任务完成结果也会被吞掉。父任务无法区分“子任务还没完成”和“完成结果被过滤”，因而无法实现正常汇合。靠等待更久不能恢复已丢弃的信息。

必须区分任务协议消息与面向人的通知。C1 的投递分类做到这一点，不需要新模块。原文称过滤“通知”，因此这主要是澄清作用域，不能直接认定原文必然会丢内部结果。

**C1 结果**：支持。免打扰不改变任务进度；需要新审批的工作仍等待用户授权。

### 5.2 补全后的功能检验表

“通过”表示给出了契约内的构造路径，不是运行测试通过，也不是对所有未来需求的完备性证明。

| 用户正常需求 | C1 内的构造方式 | 判定 |
| --- | --- | --- |
| 同一聊天并行跑调研和代码测试 | Session 关联多个 Task；各自的 executionKey / Job；结果回到原 Session | 通过 |
| 运行期间询问进展、改变要求、喊停 | 独立对话 Run、Job 观察、任务版本、授权控制信号 | 通过；外部不可中断操作须如实展示 |
| 等客户回复三天，超时再提醒 | Context 等待条件 + Channel 事件 + Clock 截止事件 | 通过 |

### 5.3 仍然不能无条件满足的需求

以下用户诉求很自然，但限制来自信息、权限或外部执行能力，不能算 8 模块分类独有的缺陷：

- “已经发出的任意消息都能撤回”：接收方或服务不支持撤回时，重新组合模块也无法收回对方看到的内容。
- “未开放接口、没有可用界面，也不给权限，仍自动读到对方的最新状态”：系统没有获得信息的通路，不能凭空知道结果。
- “手机断网、没有本地模型和执行环境，仍完成原本只在云上能做的工作”：必须改变部署或提供本地能力。
- “无论网络和服务状态如何，都在固定毫秒内给出正确答案”：需要额外的实时系统假设，普通消息队列和模型调用不能提供这种保证。

这些不能拿来凑“发现了架构缺陷”的数量。

## 6. 审查结论与实现验收点

补全后，本文检验的日常工作需求都存在 C1 契约内的构造路径，尚未找到必须突破该契约的反例。但这个结论依赖明示的契约扩展：结构化业务状态、确定性处理器、可脱离 Run 的 Job 和运行控制通路。模块数量仍为 8 不代表没有改变架构；接口允许的行为已经增加。这不是对任意需求的数学证明，也不是原百行接口无需修改的证明。

应保留的架构主张是：**8 个模块可以作为这些产品的基础职责划分，应用协议负责具体行为。** 应撤回的强主张是：**只靠连线、不实现新的状态与控制协议，就能还原所有这些产品。**

后续实现应以用户可见行为验收以下场景，而不是只检查模块是否存在：

1. 同一 Session 的长测试运行时，另一个问题能得到响应；取消后旧任务不能接受新动作。
2. 客户回复推进 Waiting 项，但其中夹带的指令不能发布为 SKILL；人的草稿编辑不被旧版本覆盖。
3. 开启免打扰时 A/B 完成消息仍到达父任务，只产生一次汇总意图。
4. 草稿更新后，旧卡片的批准不能执行新草稿；取消与执行竞态按明确生效点报告。
5. 业务状态和派发意图提交后进程退出，恢复投递仍能推进任务；不以重复消息复活已取消任务。

这些是设计级验收案例；本仓库目前只有文档，尚未执行运行时测试。

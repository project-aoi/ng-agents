# 人机分工与文稿核对

对比报告的第一份源码已就绪，第二份需要主人去要。项目先派分身处理可读材料，同时在待我处理列出需要人的动作。主人修改初稿后，后台补充仍可在参考区核对。随后主人要一份分阶段的手册，其中一步只有主人能做，中途又改了计划。

本机替身：[fixtures/uc03.sh](fixtures/uc03.sh)（`harness-a` 仓库；`harness-b` 先放在 `~/dropbox`，到第 3 步再移到 `~/dev`，代替“同事给的源码”）。

## 行为约定

**`INV-UC03-01`**　仅部分缺材料时，其他可执行分支继续推进。

**`INV-UC03-02`**　主人的动作归属项目，完成后通知对应项目，包括批准方案中列出的人工步骤。个人行动补绑项目后，由该项目接收办结回执。

**`INV-UC03-03`**　保存文稿检查版本。主人改过文稿后，文稿所属项目和主台的下一个回合收到提示，分身随后又存了新版本时也提示。后台更新与人工稿冲突时保留两份；工作台显示远端最新版供比较，后台随后保存成功的旧稿自动收回。同项目的分身可以接力编辑，多路并行时各自交付模块稿再汇总为一份面向主人的精炼主报告，无关项目不能覆盖文稿。`read_artifact` 支持分页与目录查看并直接返回结构化版本号，超过单页上限时按整页返回而非倒扣至 4 KB；大文稿版本冲突只返回当前版本与概要，不将整篇长正文倾倒进错误结果。绑定立项卡的方案仅允许发起节点和控制面（网页或外部助手）修改。

**`INV-UC03-04`**　主人要先看方案时出方案卡，批准后才立项。阶段交付按主人批准的计划推进。主人亲自做的阶段不再要求批准进入。调整计划时收回已经废弃的动作和卡片，项目记录里的目标、步骤和阶段同步。助手或主台的补充与主人原话分开，不写成主人的要求。

**`INV-UC03-05`**　新卡到达不抢焦点。决定始终基于当前卡片和明确审阅过的文稿。直接打开事项链接时优先显示该卡，方案仍有未保存修改时阻止确认。同一视图切换事项保留页面滚动，选中行离开视野时就近滚动；切换视图回到顶部。

## 端到端步骤

1. 主人：“写一份 harness-a 和 harness-b 的对比报告……b 的源码我去要，先把能做的做起来。” → 分身分析 a，待我处理出现“向同事取得源码”，另有脚本探针看目录。
2. 主人在网页改初稿（v2，加一条批注）。
3. 把 `harness-b` 移到位，主人：“源码到了，按批注改。” 分身读稿之后，主人再改一次（v3） → 后台保存冲突，旧稿停放，分身按 v3 重做成 v4。
4. 主人：“写上线手册，先出方案：①分身整理行为清单 ②我跟安全组确认默认值 ③分身写手册。” → 方案卡；批准后第二步成为主人的待办。
5. 主人：“安全组那步不用了，默认值直接按不在清单里就拒绝写。” → 人工动作和阶段卡都收回，手册区分目标策略与现有行为。
6. 主人改手册后用旧版本验收 → 被拒；用新版本验收 → 结项。

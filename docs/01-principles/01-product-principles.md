# 产品表层设计原则（GTD 极简交互与注意力准则）

> [!IMPORTANT]
> 本层文档属于**第一层：产品与架构设计原则（最高准则）**。任何新增特性、提示词调整或 Bug 修复都必须严格服从以下准则，严禁为了工程省事而向用户表层泄漏底层机制或增加用户心智负担。

---

## 一、核心定位：大脑用来做判断，工作台替人盯杂事

好用的工作辅助 Agent **不是**一个聊过二十屏就淹没全局状态的聊天框，**不是**一个把 1 条待办拆成 10 张空白子表的传统任务管理软件，**更不是**一个替人乱拍板再让人收拾烂摊子的全自动黑盒。

它的根本定位是：**与主人共用同一套极简 GTD 清单的常驻后台助手**——
- **表层永远干净直觉**：只向人类呈现收集入口、单张待拍板卡片、球权清晰的动作与结果导向的项目，以及一处可随时查看分身在做什么、直接对它发话的现场；
- **底层按粒度动态伸缩**：替人类收拢杂事、查清背景、写好初稿、盯住外部回音与门禁，把最后的判断与拍板权留给人类。

---

## 二、七条产品表层设计铁律

### `P-UX-1`：表层极简恒定，内部运行时黑话零泄漏（但严禁误伤业务专有名词）
1. **界面与对人文案绝不暴露工作台内部机制**：用户在网页、卡片、通知摘要与报告里看到的，永远是直白自然的中文业务语言——禁止把 `ng-desk` 自身的运行时概念（如“某 `cell` 正在 `claim` 信封”、“推进 `epoch`”、“进入 `serial_coalesce` 队列”）直接甩给用户。
2. **保留被分析对象的真实技术专有名词**：当任务本身是研发、代码审查或架构调研时，被分析代码库与工程领域里的标准技术概念、文件名、标识符（如源码中的 `code_cell.rs`、Git `commit`、API `token`、消息队列 `queue`、对话轮次 `turn`）**必须原样保留准确术语**，严禁机械套用禁词规则将其强行意译成晦涩的生造词。

### `P-UX-2`：一个常驻大脑，两个入口（内生主 Agent `desk` $\times$ 外部主 Agent 伴随入口）
1. **常驻 `desk` 就是主人的内生主 Agent**：
   - 在工作台里，主人与 `desk` 进行**带完整持久记录的双向对话**——问进展、商量方案、交代事情、回答它的追问，回复直接出现在对话流里（入口是「分身实况 · Agents」视图默认选中的树根节点，见 `P-UX-6`；其他视图底部的速记栏是向它发话的快捷方式）。
   - 主人离开后，同一个 `desk` 带着同一份记忆继续值守外部渠道、定时信源与跨项目协调；这些后台异步事件（信源命中、纯通知、分身汇报）静默分拣，不刷进对话，只在主人需要知道或拍板时才开口。
2. **外部主 Agent 是轻量伴随入口**：在终端或 IDE 里，主人继续和顺手的外部主 Agent（Antigravity / Claude Code / Codex CLI）对话；它经结构化控制面（MCP / `/api/agent/*`）就近查状态、把要求追加给已知的项目或直接传话给某个 `worker`、代办非 `ownerOnly` 卡片；归属不清或需要统一查重分拣的事交给 `desk` 判断，偏好与全局上下文只沉淀在 `desk` 这一个大脑里。**发完即退，绝不在当前聊天框里死循环轮询或卡住对话**。
3. **两个入口都带归属**：每条对话消息带消息标识、经入口确认的发送者身份（`owner`，或外部主 Agent 自己的 `agent:<id>`——代传时绝不冒充主人）与会话标识；回答追问时带被回复消息的标识（`replyToId`，连同被回复的原文），已知所属项目时带项目标识。转交、抄送与读历史时都能沿这些标识找回原话：网页上回答「支付仓库在哪」的路径只补给支付事项；只有当一句没指明对象的回答可能同时对应两个开放追问时，才追问一次「这是哪一个」。
4. **三层分工**：`desk` 查明一件事是否属于已有工作、决定它归谁、协调跨项目的事；`project` 对一个交付目标负责（规划、派活、验收）；`worker` 做其中一块具体工作。**服务于同一交付目标的新要求追加给原 `project`**（由它决定交给已熟悉代码的原 `worker` 还是另派一棒），不另起第二个项目；同一仓库里有独立交付与验收的事才单独立项。

### `P-UX-3`：定时监控是“信源（Source）”而非“待办”，项目列表只放有终点的事
1. 像“每周一早 9 点看核心指标”、“盯群里有没有报错反馈”、“周会前整理周报草稿”这类周期性或条件触发需求，本质是**发现和产生事项的入口**，必须归入 **信源（Mailbox Source）**，与飞书、GitHub Webhook 同层管理。
2. 平时指标正常或群内无有效反馈时，信源静默休眠（`no_hit`），**绝不在项目列表里制造永远勾不完的假待办**；只有命中异常或产出周期草稿时，才向收件箱投递一次事件。

### `P-UX-4`：按粒度分级响应——微事秒办免卡、正事备好初稿、远期想法预研停靠
不能用同一条重型审批流水线去套所有输入：
1. **个人零副作用微事（存链接、记备忘、定个人提醒）**：1～2 秒直接落库或设好到期提醒，顶栏轻提示即可，**绝不弹确认卡逼用户二次审批自己刚说的话**。
2. **需要对外回应或拍板的正事（消灭空白页）**：凡不产生外部副作用的准备工作（查代码、翻历史、拉数据、拟回复初稿），Agent 在打扰人类前先在后台做完，呈现在人类面前的永远是**带依据、带版本号的可编辑初稿**；需要人类二选一拍板的段落用 `> [!DECISION]` 显式标出。
3. **跨步骤重活（秒派后台项目接力）**：耗时编码、多仓对比、盯 CI 合入立即交由后台持久项目（`Project`）接力推进，随时接受中途追加要求或急刹。
4. **不确定做不做的远期想法（`research_then_park`）**：无需追问代码目录，趁热先派只读分身调研清楚做成结构化报告，随后自动停靠进「以后再说（`Someday`）」，平时零算力开销，日后重提或点开时不再是一行干巴巴的空白标题。

### `P-UX-5`：动作球权三分明晰，单事项至多一卡
1. 每个项目可包含多个动作，每个未完结动作必须清晰标明**当前球在谁脚下**（项目行按阻塞优先级 `我来处理 > Agent 处理中 > 等待外部` 聚合展示）：
   - **`🔵 我来处理`（`human`）**：必须人类亲自拍板、提供外部材料、验收结果或线下办理的具体物理下一步；
   - **`🟢 Agent 处理中`（`agent`）**：后台分身正在编码、调研、测试或审查；
   - **`🟡 等待外部`（`waiting`）**：球在外部流程或他人手中（如等待云端 CI 门禁、等待 MR 合入、等待同事回信或等待另一个分身让出同一目录——文案必须准确反映“等待外部条件/回复”，避免误导用户以为一定在等某人回聊天消息）。
2. **单事项至多一张待确认卡**：无论项目背后跑了多少棒子分身，同一事项在 `待确认（Clarify）` 中同一时刻最多只允许挂 **1 张**卡片；重拟初稿或补充上下文只升级原卡绑定的草稿版本，绝不刷屏连弹多张卡。

### `P-UX-6`：四视图分工（三视图管事与判断 $\times$ 第四视图管分身与现场）与专注期免打扰保护
顺应人类日常工作节奏，Web 界面固定为 **4 个核心视图 + 1 个随手记/信源抽屉**（快捷键 `1`～`4` 切换视图，`5` 打开信源抽屉，`/` 聚焦速记）。前三视图只放事项与判断，执行步骤流与聊天窗口一律不进前三视图：
1. **`待确认（Clarify）`**：单卡片拍板流（确认当前所见版本 / 口述微调 / 推迟），处理完即见清爽的 `Inbox Zero`；顶栏独立展示后台运行态与静默归档数。
2. **`专注工作区（Engage）`**：线下小事一键同步勾完；深度文档采用**左 8（初稿编辑，带人工版本防覆盖保护）右 4（参考资料包）**双栏。只在停留于专注区期间，外部 `Channel` 面向人类的非紧急通知自动缓冲（`buffered_dnd`），但后台内部 `Inbox` 接力汇报照常流转不阻塞；切到其他视图即解除免打扰。
3. **`项目全局与周回顾（Radar）`**：
   - 左栏聚焦真正有终点的活跃项目（异常悬空自动标红提醒，项目行附「N 个分身（M 个在跑）→」直达 `Agents`），以及附带**可直接点开阅读的完整报告抽屉**的「以后再说（`Someday`）」停靠专区（停靠态与在途项目的人工“已暂停”严格区分，不混挂双徽章）；
   - 右栏「15 分钟周回顾」**只干净汇总真正交付的项目级成果与人类待办完结项**，项目内部的 `worker / watcher` 中间脚手架步骤收纳于项目详情内，绝不污染周回顾列表。
4. **`分身实况（Agents）`**：管分身与现场——谁在、各自做了什么、直接对它说话：
   - **左栏三层拓扑**：信源与总助理（`desk`）→ 项目与领域中枢 → 执行分身与外部盯梢（叶节点不再派生，树深有界）。节点状态只有「运行中 / 等待外部 / 等你拍板 / 已待命 · 发消息即唤醒 / 已暂停 / 已归档」；父子连线标出项目尚未汇总的新动态（「未汇总 +N」），跨节点等待画虚线，同一工作树里的活跃分身同步高亮；随已完结项目归档的分身默认折叠。
   - **右栏工作实况流与发话框**：选中节点的派单任务书、主人的直连消息、分身的回复、折叠成一行的连续操作步骤（可展开看每一步命令与输出）、产出物与里程碑，按「精简实况 / 全量步骤 / 纯对话」三档密度阅读；发话框按节点状态切换行为——待命分身发消息即沿原上下文唤醒，运行中默认「顺手补充」（本轮收尾时吸收，不打断在跑的命令），另设「立即打断」；发给项目下分身的话自动同步给所属项目；零算力脚本节点与随项目归档的节点只读。默认选中 `desk`，即与总助理的主对话（不另设聊天抽屉）；在此视图中底部全局速记栏收起。
   - 挂着待确认卡或 `@Human` 动作的节点一键跳回 `Clarify` / `Engage`；产出物与 `Radar` 共用同一个报告阅读抽屉。
   - **此视图同样受 `P-UX-1` 约束**：状态与事件一律投影为直白中文（「待命可唤醒」「已同步给所属项目」「系统巡检唤醒」），绝不出现 `claimId`、`epoch`、`silent_inject`、`kernel.stalled_check` 之类工作台运行时词汇；分身实际触碰的本地仓库路径、Git 分支与 commit、源码文件名与标识符、终端命令与测试输出**原样等宽展示，绝不意译**。

### `P-UX-7`：权限随信任渐进放开，工程习惯按作用域即时沉淀
1. 陌生对外发送动作默认挂起等人工点卡确认；当同类固定事项连续多次零修改通过，才在回顾时顺口提议放宽或转为零 Token 脚本，绝不自作主张开启定时骚扰。
2. 当人类在对话或项目途中明确立下可复用的工程规矩（如“改完代码后直接用 `/ship-mr` 提 MR”、“某仓库的合入终审五项硬清单”），系统应立即提取**纯规则本身**（剥离单次任务细节）并支持按**目录前缀（`cwdPrefix`）与适用角色（`roles`）**精准固化为长期偏好——既让后续同类分身首轮即自动遵守，又绝不跨仓库、跨角色溢出污染无关任务。
